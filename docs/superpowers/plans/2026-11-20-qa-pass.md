# QA Pass Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give `building-phased-specs-in-parallel` an optional, bounded QA pass that exercises the finished work as a user would, fixes what it finds once, re-checks each fix once, and reports the rest before the pull request opens.

**Architecture:** One new shared script, `phase-qa`, owns the pass's state: it reads the ledger and prints the single next action, opens and lands the QA branch, closes the pass and prints the report block. Four new dispatch templates describe the planner, walker, triage and fixer roles. `SKILL.md` gains a QA step in `Finishing` that does nothing but follow `phase-qa next`. `phase-state` and `phase-schedule` are not touched.

**Tech Stack:** Bash (must run under macOS `/bin/bash` 3.2), awk, git; markdown dispatch templates; plain-bash tests under `shared/scripts/__tests__/` using `assert.sh` (`run_cmd`, `assert_eq`, `assert_rc`, `assert_contains`, `finish`).

**Spec:** `docs/superpowers/specs/2026-11-20-qa-pass-design.md`. Read it before any task; section numbers below (§4.3 and so on) refer to it.

## Global Constraints

- Work on a branch `feat/qa-pass`. Commit subjects follow the repository: `feat(parallel): …`, `test(parallel): …`, `docs: …`.
- Whole suite: `bash shared/scripts/__tests__/run-tests.sh`. One file: `bash shared/scripts/__tests__/phase-qa.test.sh`. Lint: `shellcheck shared/scripts/* skills/*/scripts/* install.sh shared/scripts/__tests__/*.sh`.
- Scripts start with `set -euo pipefail`, use no bash 4 feature (no associative arrays, no `mapfile`, no `${var,,}`), and pass `shellcheck`.
- `assert_contains` matches with a shell `case` glob: a needle must contain no `*`, `?` or `[`.
- The template tests forbid, in every template: the word `paste` outside `Do not paste`, the string `REPO_ROOT`, and the string `superpowers:`.
- Every QA template carries these lines verbatim, because the shared template loops assert them: `Repository: WORKTREE (absolute path of the run's integration worktree; use it for every shell working directory)`, `Do NOT touch the main checkout, the base branch BASE, or any phase's worktree or branch.`, `Do not spawn subagents; complete this bounded role yourself.`, a `## Return contract` heading, a `general-purpose` envelope line and a `model:` line. "The worktree boundary sentence" below means the second of these.
- Ledger lines use the em dash `—` (U+2014) with one space on each side, exactly as written below.
- `shared/scripts/phase-state` and `shared/scripts/phase-schedule` are not modified.
- For Tasks 6 to 10, which write prose an agent will follow, use superpowers:writing-skills for wording discipline. The string assertions in each task are the acceptance test.

### The QA ledger grammar

Every task uses these lines exactly. `<F>` is a flow number, `<G>` a group number, lists are comma-separated numbers or `-` for none.

```
run: qa scope — <none|top N|all|focus: words>
qa: opened — <branch> at <sha>
qa: planner dispatched
qa: flows defined — <n> found, selected <list>, not walkable <list>, parallel <yes|no>
qa flow <F>: walker dispatched
qa flow <F>: walked — <n> findings
qa flow <F>: not walked — <why>
qa: triage dispatched
qa: triaged — <n> findings, fix <G1@2 G3@2,5 …|->, <n> spec, <n> outside this run
qa group <G>: fixer dispatched
qa group <G>: fixed <sha>
qa group <G>: not fixed — <reason>
qa: verifier dispatched
qa: verified PASS — <sha>
qa: verified FAIL — <reason>
qa: landed (<sha>)
qa: not landed — <reason>
qa flow <F>: recheck dispatched
qa flow <F>: rechecked — G1 confirmed, G3 still broken, <n> new
qa: done — <summary>
qa: skipped — <reason>
```

In the `triaged` line each fix group is `G<number>@<flows>`, in fix order. The QA branch is `phase-qa-<run>`, where `<run>` is the basename of the run directory `phase-run-dir` prints.

### Index line forms in the QA files

`phase-qa report` reads these; the templates write them.

```
RUN_DIR/qa-flows.md             - [selected] F2 — checkout
                                - [not walkable] F4 — share sheet: <why>
                                - [not selected] F6 — export
RUN_DIR/qa-triage.md            - [fix] G1 — checkout: total ignores the second coupon (broken)
                                - [spec] G4 — refunds: <what is wrong> — proposed: <change>
                                - [outside this run] G5 — settings: avatar upload fails
RUN_DIR/qa-flow-<F>-recheck.md  - [confirmed] G1
                                - [still broken] G3 — <one line>
                                - [new] <one line>
```

## Review Focus

Conditions the spec implies and no happy-path test would exercise. Each has a test in the task named.

1. The controller copies a list with spaces after the commas (`selected 1, 2, 3`, `G3@2, 5`). `phase-qa next` must read it as the same list, not stall. Test in Task 2.
2. An index file is missing or has no index lines (the agent died, or wrote free text). `phase-qa report` must still print the block, with ids in place of titles, and exit 0. Test in Task 4.
3. `phase-qa land` is interrupted after the fast-forward and before the `qa: landed` line. A second call must finish the landing, not refuse. Test in Task 3.
4. `phase-qa status` fails or prints something unexpected. The status line must still print its phase summary and exit 0. Test in Task 5.
5. A fixer is dispatched again after an interruption and its commit already exists. It must report that commit, not fix the group a second time. Asserted in the fixer template, Task 8.

### Task 2: `phase-qa next`, `close` and `status`

**Files:**
- Modify: `shared/scripts/phase-qa`
- Modify: `shared/scripts/__tests__/phase-qa.test.sh`

**Interfaces:**
- Consumes: the ledger grammar above; `phase-state DESIGN_DOC` (phase rows: column 1 the number, column 2 the status); `parse-phases DESIGN_DOC RANGE` (column 1 the requested numbers), with `RANGE` read from the ledger's second line as `phase-statusline` does.
- Produces:
  - `phase-qa DESIGN_DOC BASE next` prints exactly one line: `skip <reason>`, `open`, `plan`, `walk <F> [<F>…]`, `triage`, `fix <G>`, `verify <sha>`, `land <sha>`, `push`, `recheck <F> [<F>…]`, `close` or `done`. It writes nothing.
  - `phase-qa DESIGN_DOC BASE close` appends one `qa: done — <summary>` line and prints it; exit 17 when the ledger already has one, exit 18 when `next` would not print `close` (the pass is not over).
  - `phase-qa DESIGN_DOC BASE status` prints nothing, or `<stage>`, or `<stage><TAB><done><TAB><total>`; stages are `planning`, `walking`, `triaging`, `fixing`, `verifying`, `landing`, `rechecking`. It writes nothing and always exits 0.

The rules `next` applies, first match wins. A `qa: skipped` line is *superseded* when a `batch <K>: landed`, `run: final check` or `run: qa scope` line comes somewhere after it. QA lines (`qa: …`, `qa flow …`, `qa group …`) up to and including the last superseded skip are ignored everywhere below; `run:`, `phase` and `batch` lines are always read from the whole ledger. Lines of any other shape are ignored, and spaces after commas in a list are ignored.

| # | Condition | Prints |
|---|---|---|
| 1 | no `run: qa scope` line, or the last one says `none` | `done` |
| 2 | a `qa: done` line exists | `done` |
| 3 | a `qa: skipped` line exists that is not superseded | `done` |
| 4 | no `qa: flows defined`, and a requested phase is not `merged` in `phase-state` | `skip phase <N> did not land` (lowest such N) |
| 5 | no `qa: flows defined`, and the last `run: final check` line contains `FAIL` | `skip the final check failed` |
| 6 | no `qa: flows defined`, and no `qa: opened` line after the last `batch <K>: landed` line | `open` |
| 7 | no `qa: flows defined` | `plan` |
| 8 | a `batch <K>: landed` line after `qa: flows defined` | `close` |
| 9 | flows that are selected, not in the not-walkable list, and have no `walked` or `not walked` line | `walk <those>`; only the lowest one when `parallel no` |
| 10 | no `qa: triaged`, and the `walked` lines' finding counts sum to 0 | `close` |
| 11 | no `qa: triaged` | `triage` |
| 12 | a fix group without a `fixed` or `not fixed` line | `fix <first such G in the triaged line's order>` |
| 13 | no group has a `fixed` line | `close` |
| 14 | a `qa: verified FAIL` or `qa: not landed` line, and no `push: <QA branch> ` line after it | `push` |
| 15 | a `qa: verified FAIL` or `qa: not landed` line | `close` |
| 16 | no `qa: verified` line | `verify <sha of the last 'fixed' line>` |
| 17 | no `qa: landed` line | `land <sha of the 'verified PASS' line>` |
| 18 | flows named by a fixed group that have no `rechecked` line | `recheck <those>`; only the lowest one when `parallel no` |
| 19 | otherwise | `close` |

`close` writes, first match wins:

| Condition | Line |
|---|---|
| rule 8 holds | `qa: done — abandoned, base moved under the pass` |
| no flow has a `walked` line | `qa: done — nothing to walk` |
| no `qa: triaged` line | `qa: done — <w> flows walked, no findings` |
| otherwise | `qa: done — <c> confirmed, <b> still broken, <n> not fixed, <x> new, <p> spec`, followed by `, <k> fixed but not landed` when rule 15 holds |

A fixed group is *still broken* when any `rechecked` line says so, *confirmed* when at least one says `confirmed` and none says `still broken`. `<x>` is the sum of the `<n> new` counts, `<p>` the `triaged` line's spec count. When rule 15 holds, `<c>` and `<b>` are 0 and `<k>` is the number of fixed groups.

`status` prints: nothing when rules 1 to 5 would fire or there is no `qa: opened` line; `planning` under rules 6 and 7; `walking<TAB><flows with an outcome><TAB><walkable selected flows>` under rule 9; `triaging` under 11; `fixing<TAB><groups with an outcome><TAB><fix groups>` under 12; `verifying` under 16; `landing` under 17; `rechecking<TAB><flows rechecked><TAB><flows to recheck>` under 18; nothing otherwise.

Parse the ledger once, in one awk program that `next`, `close`, `status` and (Task 4) `report` share.

- Modify: `shared/scripts/phase-qa`
- Modify: `shared/scripts/__tests__/phase-qa.test.sh`
